# PostgreSQL 面试问答整理

这份文档基于简历中“实际使用 PostgreSQL 与 pgvector 做语义检索场景开发”的表述整理，目标是帮助你在面试中把 PostgreSQL 相关问题答得更像真实做过项目，而不是只会背八股。

## 一段总述

如果面试官让你整体介绍自己的 PostgreSQL 经验，可以直接参考下面这段：

“我在毕业设计这个智能招聘辅助系统里，实际把 PostgreSQL 用在了三件事上：一是存业务数据，比如候选人、岗位和匹配记录；二是存简历解析后的半结构化结果，这部分会结合 JSONB；三是结合 pgvector 做候选人和岗位的语义匹配。我的理解不是停留在会写增删改查，而是会根据场景决定哪些数据要结构化、哪些适合半结构化、哪些适合向量化，并且知道 PostgreSQL 方案在当前规模下为什么合适、后续扩展时边界又在哪里。”

## 面试官最可能问什么

### 1. 你在项目里为什么选 PostgreSQL，而不是 MySQL？

参考回答：

“我在这个 ATS 项目里不只是拿 PostgreSQL 做普通业务库，还用到了 pgvector 做候选人和岗位画像的向量检索。相比 MySQL，PostgreSQL 对扩展能力、复杂查询、JSONB、向量检索这类场景更友好。我当时希望把业务数据、解析结果、向量检索尽量放在一个体系里，减少额外引入独立向量库带来的运维和一致性成本，所以选了 PostgreSQL + pgvector 这个组合。”

### 2. 你具体在 PostgreSQL 里存了什么数据？

参考回答：

“我主要存了三类数据：第一类是候选人和岗位的结构化业务数据，比如基本信息、技能标签、学历、经历摘要；第二类是简历解析后的中间结果，有些字段是半结构化的，我会用 JSONB 存；第三类是用于匹配的向量字段，比如候选人画像向量和岗位需求向量，用 pgvector 的 vector 类型存储，供相似度检索使用。”

### 3. 你为什么用 pgvector，而不是单独上 Milvus、FAISS 或 Elasticsearch？

参考回答：

“当时项目阶段更偏毕业设计和系统闭环验证，我优先考虑的是架构收敛和开发效率。pgvector 的优点是可以直接和业务表放在一起管理，事务一致性更自然，数据同步链路也更短。对于当前数据量和验证目标，它的能力是够用的。如果后续规模扩大到更高并发、更大向量库、更复杂召回策略，我会考虑把向量检索从 PostgreSQL 中拆出去。”

### 4. 你们做向量检索时，用的是哪种相似度？

参考回答：

“我在项目里优先考虑余弦相似度，因为招聘匹配更看重语义方向是否接近，而不是向量绝对长度。余弦相似度更适合比较候选人画像和岗位画像在语义空间中的接近程度。如果 embedding 模型本身输出已经做过归一化，内积也可以作为近似等价的方案。L2 距离我了解，但在这个场景里没有作为首选。”

补充一句：

“余弦主要看方向，内积同时受方向和模长影响，L2 看空间距离。”

### 5. PostgreSQL 里怎么写向量相似度查询？

参考回答：

“思路上就是把岗位向量作为查询向量，对候选人表里的向量列做排序，取 Top K。pgvector 提供了对应的距离操作符，可以直接在 SQL 里完成排序和筛选。业务上我一般不会只看向量分数，还会叠加结构化条件，比如学历、工作年限、技能关键词，做一个混合筛选。”

### 6. 你做过哪些 PostgreSQL 优化？

参考回答：

“我做过的优化主要是工程上比较实用的几类。第一是给常用过滤条件和关联字段建索引，比如外键、状态、创建时间等。第二是避免把所有信息都塞进大字段里，对高频查询字段尽量结构化。第三是关注分页和排序场景，避免无条件大范围扫描。第四是在向量检索上控制候选集规模，不会把所有复杂条件都留给最后一层排序。”

如果面试官继续问有没有看执行计划，可以补一句：

“有用过 EXPLAIN 和 EXPLAIN ANALYZE 看查询是不是走了预期索引，至少在定位慢查询时这是必要的。”

### 7. 你了解 PostgreSQL 的 JSONB 吗？为什么会用？

参考回答：

“了解。我在简历解析场景里，原始提取结果天然是半结构化的，比如技能列表、项目片段、证书、模型抽取出的补充字段，这类数据如果一开始就强行完全表结构化，迭代成本会比较高。所以比较适合先用 JSONB 存原始或扩展信息，再把高频检索字段拆出来单独建列。这样兼顾灵活性和查询性能。”

### 8. 你了解 PostgreSQL 的事务和 MVCC 吗？

参考回答：

“我知道 PostgreSQL 用 MVCC 保证并发下的读写隔离，读操作不会简单地被写操作阻塞。事务上我在项目里主要关注的是，简历解析结果入库、匹配任务状态更新这类操作要保持一致性，不能出现主记录更新了但明细或状态没同步的情况。理论上我也知道隔离级别、脏读、不可重复读这些概念，但在我这个项目里更多是用 Spring 事务把一组数据库写操作包起来保证一致性。”

### 9. PostgreSQL 和 MySQL 在你看来最大的区别是什么？

参考回答：

“如果放在我这个项目语境里，最大的区别不是谁更强，而是谁更适合当前需求。MySQL 很适合常规业务系统，但 PostgreSQL 在扩展类型、复杂查询、JSONB、向量检索这类场景更顺手。我的项目同时需要事务型业务存储和语义检索能力，所以 PostgreSQL 更合适。”

### 10. 如果数据量继续增长，你觉得 PostgreSQL + pgvector 会遇到什么问题？

参考回答：

“主要会遇到三个方向的问题。第一是向量检索性能，随着候选人规模上升，召回延迟和索引维护成本会上来。第二是混合查询复杂度，结构化过滤和向量排序叠加后，执行计划会更难控制。第三是资源竞争，业务事务和向量检索都压在同一个库上，可能影响稳定性。后续如果规模继续扩大，我会考虑把检索层和事务层做更明确的职责拆分。”

## 快问快答 10 题

### 1. PostgreSQL 和 MySQL 的主要区别是什么？

“如果从我项目视角看，PostgreSQL 的扩展能力和复杂数据支持更强，比如 JSONB、向量扩展、复杂查询；MySQL 更偏传统业务场景。我的 ATS 项目既要做业务存储，又要做语义匹配，所以 PostgreSQL 更适合。”

### 2. PostgreSQL 的 JSON 和 JSONB 有什么区别？

“JSON 更偏原始文本存储，保留输入格式；JSONB 会做二进制化处理，查询和索引能力更好。项目里如果只是保留原始报文可以用 JSON，但如果需要筛选和查询，通常更适合 JSONB。”

### 3. 什么是 MVCC？

“MVCC 是多版本并发控制。它的核心作用是让数据库在并发读写时，不需要简单地用读写互斥来保证一致性，而是通过数据的多个版本让读操作看到合适的快照。这样并发性能会更好。”

### 4. 事务的四个隔离级别你了解吗？

“了解。分别是读未提交、读已提交、可重复读、串行化。PostgreSQL 默认是读已提交。隔离级别越高，一致性越强，但并发代价也越高。项目里一般根据业务一致性要求来选，不会盲目拉满。”

### 5. PostgreSQL 默认隔离级别是什么？

“默认是读已提交。也就是一个事务只能看到其他事务已经提交的数据。”

### 6. 索引有什么作用？什么时候不适合建索引？

“索引主要是减少查询扫描范围，提高检索效率。高频过滤、排序、关联字段通常适合建索引。但索引不是越多越好，因为它会增加写入和维护成本。如果字段区分度很低、更新特别频繁，或者几乎不查，就不一定值得建索引。”

### 7. B-Tree 索引适合什么场景？

“B-Tree 是最常见的通用索引，适合等值查询、范围查询、排序场景。大多数普通业务字段索引，默认优先考虑 B-Tree。”

### 8. 你怎么排查一条 SQL 为什么慢？

“我通常先看查询条件和数据量，再看有没有命中合适索引，然后看排序、分页、关联是不是把扫描范围放大了。再进一步会看执行计划，确认数据库是不是走了我预期的路径。”

### 9. 什么是 EXPLAIN？你怎么用？

“EXPLAIN 用来查看 SQL 的执行计划，能看出数据库准备怎么执行这条语句，比如走没走索引、是否顺序扫描、连接方式是什么。实际排查慢查询时，我会先用它判断问题是在 SQL 写法、索引设计，还是数据分布。”

### 10. 为什么你项目里用 PostgreSQL 的 pgvector？

“因为我要做人岗语义匹配。普通数据库表只能很好地处理结构化条件，但招聘场景里还需要比较候选人与岗位描述在语义上的接近程度。pgvector 让我能直接在 PostgreSQL 里存向量并做相似度检索，适合我这个项目当前阶段的架构收敛需求。”

## 再补 5 个一句话答案

### 1. 主键一定会自动有索引吗？

“会，主键约束通常会自动创建唯一索引。”

### 2. 唯一索引和普通索引区别是什么？

“唯一索引要求索引值不能重复，普通索引只负责加速查询，不负责唯一性约束。”

### 3. 为什么不把所有字段都放 JSONB？

“因为灵活性高不等于查询高效，高频过滤和关联字段还是应该结构化建列，否则性能和约束能力都会变差。”

### 4. 数据库事务在项目里解决什么问题？

“保证一组相关写操作要么一起成功，要么一起失败，避免部分更新成功导致数据不一致。”

### 5. 向量检索能不能完全替代结构化筛选？

“不能。招聘场景必须把学历、年限、地点、技能门槛这类硬条件和语义检索结合起来。”

## 最稳的答题模板

每道题尽量按下面三步答：

1. 先用一句话给定义。
2. 再说它在项目里有什么意义。
3. 最后补一句工程取舍。

示例：

“JSONB 是 PostgreSQL 对半结构化数据更友好的存储方式，支持更好的查询和索引。在我的简历解析场景里，它适合存扩展字段。但高频筛选字段我不会全放进去，还是会结构化建列。”

## 你要避免的答法

1. 不要说自己精通 PostgreSQL。更合适的定位是项目中实际使用过，并且能讲清楚设计取舍。
2. 不要空讲八股，比如一直背事务隔离级别，却说不出自己项目里存了什么。
3. 不要把 pgvector 吹成万能方案。成熟答法一定要承认它有规模边界。
4. 不要把 PostgreSQL 说成只是为了听起来高级。一定要绑定 ATS 项目场景。

## 临场策略

1. 如果对方问得浅，就往项目落地上答。
2. 如果对方问得深，就用“我在项目中的实际使用边界是这里”来收口。
3. 如果对方故意压你，就强调工程取舍，而不是硬装成数据库专家。
